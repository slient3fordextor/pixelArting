# 技术选型与跨引擎接入决策

状态：MVP 技术决策。本文记录当前选择和约束；如果实现中的测量结果推翻这些假设，应更新本文并同步 MVP、技术架构和素材格式文档。

## 1. 决策结论

MVP 使用 **Python 3.12 + FastAPI** 作为核心服务语言，使用 Pillow/NumPy 实现像素读取、质检、确定性修复和导出。后台任务使用独立 Python worker 执行。

Go 不作为 MVP 的第二套核心处理实现。等素材协议和规则行为稳定后，再按实际瓶颈选择 Go 的使用范围：

- 本地文件监听、批量导入和 CI 命令行工具；
- 需要常驻运行的本地代理；
- 与引擎通信的轻量桌面 agent；
- 经性能测试确认需要的高并发或低资源服务。

如果 Go 组件处理素材，必须调用同一套版本化规则和素材协议，不能在 Go 中复制一套行为相近但结果不同的质检/修复逻辑。只有经过固定样例集的结果对比，才允许把某个处理器迁移到 Go。

## 2. 为什么 MVP 先用 Python

项目首期的风险在于规则定义、像素修复、调色板和生成流程是否正确，而不是服务吞吐。Python 的图像处理和模型调用生态更适合快速验证这些行为：

- Pillow 可以直接读取 PNG、访问 RGBA 像素、执行最近邻缩放和调色板处理；
- NumPy 适合批量比较像素、计算颜色集合和生成差异掩码；
- AI 提供方通常优先提供 Python SDK，失败重试、来源记录和实验脚本更容易复用；
- pytest 能用固定图片和边界案例快速覆盖每条规则；
- FastAPI/Pydantic 可以先固定 API 和数据校验，再决定哪些模块需要拆分。

Go 的优势是单文件部署、低资源占用和并发模型简单，但 MVP 需要的图像算法和实验代码会引入更多库选型与自定义实现。除非基准测试显示 Python 无法满足目标，否则不为预期性能提前承担双语言维护成本。

## 3. MVP 服务形态

首期采用一个模块化后端应用和一个独立 worker，不把每个逻辑模块拆成独立微服务：

```text
Web Client
    |
FastAPI API
    |---- Project / Asset / Version
    |---- Quality Rules
    |---- Repair Executor
    |---- Export Adapters
    |---- Generation Adapter
    |
Redis + Python Worker
    |
PostgreSQL + File/Object Storage
```

同步接口只执行轻量的元数据校验和查询。生成、批量检查、修复预览、导出和大文件处理返回任务 ID，由 worker 执行并持久化状态。API 进程和 worker 必须使用相同的规则、修复、素材协议和执行器版本。

已确认本地第一版使用 SQLite、文件存储、有界同步处理，Redis/worker 后置到生成和批处理阶段。存储接口与业务隔离，后续可切换 PostgreSQL 和 S3 兼容对象存储；协议不含本机绝对路径。覆盖与限制见 [实现状态](implementation-status.md)。

首期目标为 64×64、多图层、Godot 4.7.2。引擎使用合成 PNG，层图和属性保留在伴随 JSON 中。

本地交付入口确认为独立桌面窗口，采用 Electron 承载 React 并自动管理 Python 服务；当前不提供浏览器启动入口。工作区启动方式、右键交互和分发限制见 [桌面客户端](desktop-client.md)。此选择不引入第二套素材处理实现。

## 4. 跨引擎接入原则

跨引擎兼容由**协议和适配器**保证，不由共享插件语言保证。

统一服务层负责：

- 素材版本、帧、动画、调色板、原点和碰撞框的语义；
- 8 条 MVP 规则和 5 个 MVP 修复动作；
- 报告、Finding、修复计划、任务状态和错误码；
- PNG、帧序列、Sprite Sheet、JSON 和版本 checksum；
- API 的版本、认证、幂等键和并发版本检查。

引擎适配器负责：

- 在引擎中选择文件、节点或资源；
- 将引擎资源转换为统一输入格式；
- 调用 API 或本地 agent；
- 将明确支持的导出包写回引擎目录；
- 报告引擎版本、导入结果和不支持的字段。

适配器不能重新实现规则，也不能静默丢弃统一格式中的原点、帧时长或碰撞数据。无法表达的字段必须显示警告或拒绝导出。

## 5. 插件语言和连接方式

| 引擎 | 插件实现 | 首选连接 | 责任边界 |
|---|---|---|---|
| Godot | GDScript 或 C# | HTTP/JSON；后续可调用本地 agent | 资源选择、导入 SpriteFrames、展示报告 |
| Unity | C# Editor extension | HTTP/JSON；后续可调用本地 agent | 资源选择、导入 Sprite/Atlas、展示报告 |
| RPG Maker | JavaScript 插件 | HTTP/JSON | 资源路径、命名和导入结果 |
| 其他引擎 | 使用其原生插件语言 | HTTP/JSON 或 CLI | 只实现该引擎的资源映射 |

Go 本地 agent（若后续需要）只提供稳定的本地协议代理：负责发现服务、文件权限、任务转发、下载和导入触发，不复制规则实现。插件使用短期 token 或本地受限连接，不把云端 API key 写入引擎项目。

## 6. 统一协议约束

HTTP API、JSON 交换格式和导出包都必须带版本。至少包含：

```text
schemaVersion
assetVersionId
ruleVersion / fixVersion
executorVersion
targetEngine / targetEngineVersion
checksum / manifest
```

质检、修复和导出均绑定明确的 `assetVersionId`。确认修复或更新当前版本时提交 `expectedCurrentVersionId`；版本不一致返回冲突，不能把旧预览套到新版本。

确定性规则和修复必须在 Python 与未来 Go 实现之间使用同一固定样例集做像素级、元数据级和错误状态级对比。仅 checksum 相同不足以证明错误处理等价；测试还要比较 Finding、skip/fail 状态和导出文件清单。

## 7. 何时引入 Go

只有满足以下至少一项，才新建 Go 组件：

1. 有基准数据表明 worker 的 CPU/内存或启动时间成为实际瓶颈；
2. 需要一个不依赖 Python 环境的本地 agent 或 CLI；
3. 文件监听、批量同步或网络代理需要长时间常驻运行；
4. 部署环境明确不能提供 Python 运行时。

引入顺序建议为：先实现协议兼容的 Go CLI/agent，再迁移一个边界清晰的确定性处理器，最后才考虑迁移 API 服务。AI 生成适配、规则定义和验收样例继续以 Python 实现为参考实现，直到跨语言结果稳定。

## 8. 不在当前决策中的内容

- 不承诺 Python 和 Go 都能直接作为 Godot/Unity/RPG Maker 插件语言；插件应使用引擎支持的原生扩展机制。
- 不因为使用 Go 就自动获得多引擎兼容；兼容性来自协议版本、适配器测试和干净引擎项目回读。
- 不在 MVP 阶段拆成多个独立微服务；模块名是职责边界，不是部署边界。
- 不在没有样例、性能和成本数据时承诺迁移到 Go 或替换图像库。

## 9. 验证门槛

技术选型在以下检查通过前保持可调整：

- Python 参考实现覆盖 8 条规则、5 个修复和固定边界样例；
- API 客户端可以在不依赖引擎的情况下上传、质检、预览修复、创建版本和导出；
- Godot 目标版本能从干净项目加载 SpriteFrames 包；
- 至少一个引擎适配器完成真实资源的导入回读；
- 记录上传、质检、修复和导出的耗时、内存、失败率及单位成本；
- 若 Go 原型出现，必须与 Python 参考实现通过同一结果对比测试。
