## 2. MVP 功能矩阵

| 能力 | MVP 范围 | 后续版本 |
|---|---|---|
| 用户与项目 | 用户只能访问自己的私有项目、素材和任务；项目保存画布、调色板、检查配置 | 团队角色、审批、协作 |
| 素材输入 | 新建空白素材、PNG 单图、明确指定网格的 PNG Sprite Sheet、文本生成角色；真实缩略图和确认删除 | Aseprite 原生导入、更多素材类型 |
| 素材规格 | 单帧目标画布 64×64；角色四方向 `down/left/right/up`；`idle/walk` | 八方向、其他动作、Tileset、VFX |
| 生成 | 候选预览、选定角色后生成方向和动作；保留来源记录；效果必须先验证 | 自训练模型、风格记忆 |
| 编辑 | 多图层铅笔、橡皮、取色、填充、直线、矩形、椭圆、矩形选区复制/剪切/粘贴/删除/移动、画布移动、单图层像素拖动、原点/基线参考标记、颜色选择、帧选择与排序、动画播放、自动保存草稿与恢复；层顺序、名称、显示、锁定、不透明度、复制和右键操作 | 图层组、复杂混合模式、复杂选区变换/羽化、文字/渐变/模糊和完整编辑器工具集 |
| 质检 | 8 条确定性规则，可独立开关；显示问题位置与跳过原因 | 抗锯齿启发式检测、语义漂移、Tileset、碰撞和图层检查 |
| 修复 | 5 个确定性动作；预览、确认、创建版本、重新检测 | AI 局部重绘、碰撞框生成、Tileset 修补 |
| 版本 | 保存、修复产生不可变版本；版本浏览和恢复；草稿撤销/重做 | 团队审批、版本合并 |
| 导出 | PNG 单图、帧序列、Sprite Sheet、JSON 和 Godot SpriteFrames 包 | Godot TileSet、Godot 插件、Unity、RPG Maker、Aseprite 原生导出 |

单张 PNG 可以质检和修复，但不能被当作完整四方向角色；用户必须补齐对应动画后才能通过完整角色验收。

角色完整性建议使用 `idle` 每方向 1 帧、`walk` 每方向 4 帧作为首批验收样例。实际帧数和时长由配置明确指定，不将该建议硬编码成所有素材的限制。

明确不包含：完整游戏制作、3D、多人实时协作、公共素材市场、自定义规则 SDK、面向用户的 CLI 和收费系统。订阅与计费保留为商业验证方向。

## 3. 用户流程与异常状态

### 3.1 上传、质检、修复和导出

1. 创建项目，配置画布、调色板、动作帧数和透明度策略。
2. 上传文件；Sprite Sheet 必须确认单元格尺寸、间距、边距和动作/方向映射。
3. 保存原文件与初始版本，展示切分预览。布局不明确时要求确认，不猜测动作。
4. 执行选中的规则，分别展示问题、跳过和执行失败；跳过不能显示为通过。
5. 选择修复，查看像素差异、尺寸与元数据变化，再确认应用。
6. 原子提交新版本并重新质检，用户检查动画播放效果。
7. 导出指定版本；先做不可关闭的包完整性验证，再生成下载包。

生成流程增加提示词、候选选择和模型任务状态，其后使用同一质检/修复/导出流程。

### 3.2 必须设计的状态

| 情况 | 预期行为 |
|---|---|
| 文件解码失败、布局不能完整切分 | 解释失败原因；保留已上传的原文件，不发布无效可编辑版本 |
| 生成失败、取消或部分方向缺失 | 显示任务结果与缺失项；有效部分可作为候选保存，不宣称完整成功 |
| 没有调色板或基线标记 | 相应规则标为跳过并提示缺少的输入 |
| 修复会删除有效像素或元数据越界 | 拒绝该修复或要求调整参数，不静默裁切 |
| 预览后当前版本发生改变 | 拒绝提交旧预览；重新基于当前版本生成预览 |
| 切换版本或离开时有未保存草稿 | 提供保存、放弃和继续编辑选项 |
| 删除素材 | 先确认删除素材及其全部版本；当前版本已变化则拒绝删除；不影响其他素材 |
| 导出检查失败 | 展示具体缺失项，不返回表面成功但无法加载的包 |

## 4. 开发阶段

### 阶段一：上传处理闭环

完成独立 React/Electron 工作台、私有项目隔离、PNG 输入、统一素材结构、版本、8 条规则、5 个修复和 PNG/JSON 导出。先证明已有素材能安全处理。

### 阶段二：完成 MVP

完成多图层像素编辑、四方向 idle/walk 的生成流程与播放，以及 Godot SpriteFrames 导出。在 Godot 4.7.2 的干净项目中验证加载；PNG 合成可见图层，JSON 包保留每层图像和属性。

只有阶段一和阶段二都通过才称为 MVP；阶段一只是可试用的上传处理原型。生成可行性实验应提前开展，不能等第二阶段开发结束才验证。

### MVP 之后

引擎插件、其他引擎、Tileset、AI 语义质检和局部修复、团队能力依次依据试用反馈排期，不属于首期承诺。

## 5. 验收场景

| 场景 | 可检查的通过条件 |
|---|---|
| 合规角色 | 指定四方向和动作齐全；帧数与配置一致；帧时长有效；画布为 64×64；预期规则通过 |
| 多图层 | 增删、顺序、显示、锁定与透明度跨帧/跨版本保存；隐藏层可恢复；合成 PNG 与分层包内容对应 |
| 问题样例 | 超色、调色板外颜色、半透明、尺寸异常、缺帧、基线不齐、锚点越界和无效导出引用分别得到预期结果 |
| 规则开关 | 禁用规则不执行、不产生 Finding；缺前置输入的规则显示跳过；执行异常不会被计为通过 |
| 修复安全 | 原文件与父版本内容不变；失败不发布半成品；重复确认不创建重复版本 |
| 修复正确性 | 参数和修复前后像素/元数据差异可检查；重检判断问题是否消除；不能只以 checksum 变化判定成功 |
| 版本恢复 | 切换至历史版本后像素和元数据一致；旧报告保持原绑定，不冒充当前版本报告 |
| 可复现 | 相同输入、规则/修复版本和配置的确定性结果一致；随机生成不纳入该承诺 |
| Godot 导出 | 包内路径可解析；四方向 idle/walk 可加载播放；无缺失纹理；帧顺序和时长匹配 |
| 私有隔离 | 另一个用户不能通过资源 ID、任务 ID 或文件下载地址读取/修改素材 |

固定测试集应包含合规、违规、合法例外和边界样例，并记录人工预期。人工反馈和豁免与原报告分开保存，不能通过隐藏 Finding 改写检测历史。

## 6. 生成能力验证

先用固定角色描述和参考图比较候选模型/流程：记录原始分辨率、像素化步骤、方向和动作生成方式、人工修改时间、失败次数、延迟和实际费用。对比角色身份、服装配色和动作可读性时保留人工评分，不以规则通过替代视觉质量。

生成记录保存模型及版本、参数、提示词引用、参考图校验值、可用时的 seed 和费用；seed 不能被视为跨模型可复现的保证。商业使用信息记录为有来源的说明或未知状态，不由质检结果推断授权。

若四方向动画无法达到验收目标，应显式调整范围并同步文档；不能悄悄以单张生成替代承诺。

## 7. 实现前需要确认的事项

| 待决项 | 定稿依据 |
|---|---|
| 生成提供方与处理链 | 固定样例质量、费用、调用限制及来源记录能力 |
| Godot 兼容验收 | 已指定 4.7.2，仍须在该版本完成导入回读；不承诺跨版本兼容 |
| 调色板、帧数、时长和透明度默认值 | 首批真实角色样例；当前建议限制 32 种可见 RGB 色、禁止半透明 |
| 文件大小、像素数、帧数与任务上限 | 解码内存和耗时测试；实施前必须明确数值 |
| 认证和部署演进 | 本地原型先用单用户、SQLite/文件存储、有界同步接口；完整 MVP 多用户与 worker 后续实现 |
| 性能、生成成功率和单位成本门槛 | 试用前先固定测量口径、目标值和样本，不追认结果为目标 |

当前语言和接入决策已经确定：MVP 采用 Python + FastAPI + Python worker；引擎插件使用各自原生语言，通过版本化 HTTP/JSON 协议接入。Go 仅作为后续本地 agent、CLI 或经基准测试证明必要的服务组件，具体约束见 [技术选型](technology-selection.md)。

尚待验证的事项不能视为已通过。运行命令和依赖见 README，worker 和 AI 调用的步骤随相应实现补充。
